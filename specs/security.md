# Rucene — Security Specification

**Spec ID:** SEC  
**Scope:** Threat model, input validation, resource limits, memory mapping, file-system paths, and dependency policy.

## 1. Threat model

Index files are treated as **potentially malicious network payloads** by default. Rucene must handle malformed, corrupted, or adversarially crafted index files without panicking, leaking sensitive information, or consuming unbounded resources.

## 2. Failure posture

- All parsing failures must return a recoverable `Result<T, LuceneError>`.
- Controlled panics are not acceptable as a normal error path for malformed input.
- Error messages must avoid disclosing filesystem paths or internal structures when the input origin is untrusted.

## 3. Resource limits

Rucene enforces **configurable** resource limits to bound the impact of malicious indexes:

- Maximum index / segment file size.
- Maximum number of documents, terms, fields, and open file handles.
- Per-query and per-server memory ceilings.
- Maximum recursion depth for tree-like formats.

Defaults are chosen to cover typical production workloads; callers can tighten or relax them.

## 4. Trusted vs. untrusted indexes

The API explicitly distinguishes between **trusted** and **untrusted** indexes:

- **Trusted indexes:** internal indexes generated by the same application or a verified pipeline. Memory mapping is permitted.
- **Untrusted indexes:** any index from an external source. Memory mapping is disabled; buffered I/O is used instead.

Process-level isolation for untrusted indexes is the responsibility of the caller; Rucene documents this expectation clearly.

## 5. File-system path handling

Rucene does not impose additional path restrictions beyond what the host operating system provides. Callers that open untrusted indexes are expected to run inside an appropriately sandboxed environment.

## 6. Dependencies and supply chain

- Keep external dependencies minimal.
- All dependencies must use permissive, OSI-approved licenses (e.g., MIT, Apache-2.0).
- Versions are pinned in `Cargo.lock` and reviewed before upgrades.
- Crates containing `unsafe` code require explicit review and justification.

## 7. Fuzzing and security testing

- Property-based tests (`proptest`) cover critical parsing paths from the first sprint.
- Fuzzing targets are added for every codec and `IndexInput` parser that consumes external bytes.
- Discovered crashes are converted into regression/portability tests before the underlying bug is closed.

## 8. Acceptance criteria

A task touches security-relevant code when it:

- Parses external bytes.
- Allocates memory based on external sizes.
- Performs file-system operations.

Such tasks must include tests with malformed/crafted inputs and must not introduce `unsafe` without review.
