# Decision: StandardTokenizerImpl Porting Strategy

## Context

Rucene Sprint 2 must port `org.apache.lucene.analysis.standard.StandardTokenizer` and its underlying `StandardTokenizerImpl`. The reference implementation in Apache Lucene Core 10.5.0 is generated by [JFlex](https://jflex.de/) from `StandardTokenizerImpl.jflex`, which encodes the Unicode Text Segmentation algorithm (UAX #29) for Unicode 12.1.

The JFlex-generated Java source is ~40 KB of scanner tables and state-machine code (`StandardTokenizerImpl.java`). It is not feasible to translate it line-by-line into Rust without a high risk of silent divergence in token boundaries.

## Options evaluated

| Option | Fidelity | Maintenance | Effort | Verdict |
|--------|----------|-------------|--------|---------|
| A. Port the generated JFlex Java scanner manually to Rust | Highest | Hard | Very large | Rejected for Sprint 2: too much code, high risk of table errors, and hard to keep in sync with Unicode updates. |
| B. Generate Rust from the `.jflex` source using a custom code generator | Highest | Hard | Very large | Rejected: no maintained JFlex-to-Rust generator exists; building one is out of Sprint 2 scope. |
| C. Use a Rust Unicode-segmentation crate and add token-type classification | Good for common text | Medium | Medium | **Selected** as the pragmatic path for Sprint 2. |
| D. Hand-write a UAX #29 state machine from scratch | Highest | Hard | Large | Rejected: essentially reimplementing JFlex by hand. |

## Selected strategy

**Option C: hybrid segmentation + classification.**

1. Use the `unicode-segmentation` crate (Apache-2.0/MIT) to obtain UAX #29 word boundaries. This covers the bulk of the rules that `StandardTokenizerImpl` implements.
2. Classify each segmented word into one of the Lucene token types:
   - `<ALPHANUM>`: alphabetic + numeric sequences
   - `<NUM>`: numeric sequences
   - `<SOUTHEAST_ASIAN>`: Thai/Lao/Myanmar/Khmer complex-context scripts
   - `<IDEOGRAPHIC>`: Han (CJK) ideographs
   - `<HIRAGANA>`: Hiragana
   - `<KATAKANA>`: Katakana
   - `<HANGUL>`: Hangul
   - `<EMOJI>`: emoji sequences (including ZWJ, tag, keycap, flag sequences)
3. Implement the `StandardTokenizer` wrapper exactly as in Lucene:
   - `set_max_token_length` / `max_token_length`
   - `increment_token` loop that chops or skips over-long tokens
   - `end()` final-offset logic
   - `reset()` / `close()` scanner reset
4. Add a **portability test corpus** that compares Rucene token boundaries, types and offsets against Java Lucene 10.5.0 output on the same input. Any divergence becomes a regression test that drives incremental fixes.

## Known parity gaps

- `unicode-segmentation` follows UAX #29 but may not use the exact same Unicode version or word-break property assignments as Lucene 10.5.0 (Unicode 12.1). Boundary differences are expected in edge cases.
- The Lucene scanner has custom emoji-sequence handling derived from TR #51. `unicode-segmentation` may produce different emoji boundaries; this area will be prioritized in portability testing.
- Case-folding and presentation-selector handling may differ.

## Incremental fidelity plan

1. Sprint 2 delivers a working `StandardTokenizer` with the hybrid approach and a basic multilingual portability test.
2. Divergences detected by portability tests are documented and fixed in follow-up tasks (either by adding custom rules before/after segmentation or by gradually replacing crate-based segmentation with a custom implementation if the gap is large).
3. The long-term goal remains 100% token-boundary parity; the hybrid approach unblocks the rest of the search pipeline while the fidelity work continues.

## Decision record

- **Decision:** Use `unicode-segmentation` + token-type classification for the Sprint 2 `StandardTokenizer` implementation.
- **Rationale:** Balances correctness, effort, and maintainability; unblocks downstream analysis/search work immediately.
- **Risk:** Boundary/emoji divergence from Java Lucene; mitigated by portability tests and incremental fixes.
- **Date:** 2026-08-03
