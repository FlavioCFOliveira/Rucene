# Rucene 0.2.0 Release Notes

**Version:** 0.2.0
**Date:** 2026-11-27
**Code commit:** `0306398d` (`release/0.2.0`): `develop` at `070015e6`, plus the version fields, documentation, `NOTICE`, `licenses/` (`3b48d6a5`) and the release fixes (`0306398d`)
**Previous release:** [0.1.0](0.1.0.md) (`v0.1.0`, 2026-11-21)
**Target:** Apache Lucene Core 10.5.0

## Overview

Rucene is a Rust port of Apache Lucene 10.5.0 that aims at functional parity
and index-file compatibility with it. Release 0.2.0 covers the 97 commits from
`v0.1.0` to `070015e6` (sprints 17 to 20 of the `rucene` roadmap) and the
release fixes of `0306398d`.

This release:

* ports eight more Lucene modules: `memory`, `facet`, `highlighter`,
  `spatial3d`, `spatial-extras`, `spatial-test-fixtures`, `benchmark` and
  `analysis/icu`, with their tests;
* ports the parts of ICU4J 77.1, spatial4j 0.8, s2-geometry-library-java 1.0.0
  and NekoHTML 1.9.17 (with Xerces-J 2.12.2 and SAX 2.0.2) that these modules
  use;
* plugs ported `rucene` elements where Lucene plugs them (sprint 19);
* compares Rucene with Lucene on Lucene's own `byTask` benchmark and makes
  Rucene faster on 17 of 20 algorithms, as measured at `2c4f248c` (sprint 20);
* **changes the public API of `rucene` incompatibly and raises the minimum
  Rust version to 1.100** (see
  [Breaking changes and migration](#breaking-changes-and-migration)).

The complete, sourced list of changes, each with its commits and `rmp` tasks,
is in [`CHANGELOG.md`](../../CHANGELOG.md#020---2026-11-27). The Knowledge
Graph coverage and divergence figures of 0.1.0 were not re-measured for this
release.

## Highlights

* **Eight new Lucene modules**, each checked against Lucene 10.5.0 by its own
  Java-oracle tests (`crates/<crate>/tests/*_oracle.rs`) and by its ported
  Lucene tests.
* **Lucene's benchmark, in Rust**: `rucene-benchmark` runs Lucene's
  `conf/*.alg` files unchanged, and `tools/bench-compare` runs the same
  algorithm on Lucene 10.5.0 and Rucene and prints both reports side by side.
* **Faster than Lucene on 17 of 20 benchmark algorithms**, measured at
  `2c4f248c`, before one release fix (see
  [Performance compared with Lucene](#performance-compared-with-lucene)).
* **Fixes** to `%f` rounding in similarity explanations,
  `SoftDeletesDirectoryReaderWrapper` with binary doc values,
  `TotalTermFreqValueSource`, and the order of `BooleanScorer`'s collection,
  which diverged from Lucene's.

## Breaking changes and migration

These changes affect code that uses the `rucene` API. Each is listed with its
commit and task in the CHANGELOG.

| Change | Migration |
|---|---|
| Minimum supported Rust version is **1.100** (was 1.89) in every manifest, by user decision. The code needs at least 1.95.0, the first release with `if let` guards on match arms (`f4a54f53`); 1.100 is a policy choice above that minimum, the version every release gate ran on. | Build with Rust 1.100 or later. |
| `LuceneError` is `pub struct LuceneError(Box<LuceneErrorInner>)` and dereferences to `LuceneErrorInner`, so a `Result<T>` of a small `T` is returned in registers (`f4a54f53`). | Replace the struct pattern `LuceneError { kind: …, .. }` with `matches!(error.kind, LuceneErrorKind::…)`, `error.kind()` or `error.into_kind()`. |
| `SortedDocValues::terms_enum` / `intersect` and the `SortedSetDocValues` equivalents take `&mut self` and return `Box<dyn TermsEnum + '_>`; both traits require `Send` (`e6a0bf9b`, `f7151f46`). | Implementors: change the two signatures and make the type `Send`. Callers: keep the values alive while the terms enum is used. |
| `SortedDocValuesTermsEnum<P>` and `SortedSetDocValuesTermsEnum<P>` take `P: DocValuesRef` (implemented for `&mut V`, `Box<V>`, `Arc<Mutex<Box<V>>>`) (`f7151f46`). | `new(Box<V>)` compiles unchanged; replace a written type such as `SortedDocValuesTermsEnum<dyn SortedDocValues>` with the `P` you pass. |
| `FilteredTermsEnum<'a>`, `TermsEnumIndex<'a>` and `AutomatonTermsEnum::new` carry the lifetime of the wrapped terms enum (`e6a0bf9b`). | Add the lifetime; use `'static` for an owned terms enum. |
| `HnswUtil::graph_is_rooted(reader, vector_field)` has no third parameter (`412b9ff2`). | Drop the `graph_of_leaf` argument. |
| `DocIdSetBuilder::build` returns `Box<dyn DocIdSet + Send + Sync>` (`d58abe96`). | Coerces to `Box<dyn DocIdSet>`; only explicit type annotations change. |
| LZ4 `compress` and `compress_with_dictionary` are generic over `O: DataOutput + ?Sized` and `H: Lz4HashTable + ?Sized` (`7e5a6923`). | Calls compile unchanged; a function-pointer use needs the type parameters. |

`search::bayesian_score_estimator::JavaRandom` moved to
`util::java_random::JavaRandom`; the old path still re-exports it.

No cargo feature changed. `rucene` drops its unused `tokio` dependency
(`0306398d`) and adds none. No commit or task of this release records a change to an index file
format; the portability tests in [Test evidence](#test-evidence) cover them.

## Performance compared with Lucene

**Source:** the sprint 20 `FINDING` of 2026-11-27 (roadmap `rucene`), which
closed the optimisation campaign at commit `2c4f248c`.

**Caveat:** these figures were measured at `2c4f248c`, before the release fix
`0306398d` removed the batch `collect_stream` path of
`BooleanScorer::score_window_single_scorer`, which made Rucene's collection
order diverge from Lucene's. That path came from `49502b4b`, which reported
−4.0 % instructions on `standard` search for the whole commit. The share that
the removal gives back was not measured, and the figures below were not
re-measured after it.

**Method** (`tools/bench-compare/README.md`; sprint 20 log):

* Workload: the `byTask` algorithms of Lucene 10.5.0 `lucene/benchmark/conf`,
  run unchanged by both engines on Reuters-21578, extracted by Lucene's own
  `ExtractReuters`.
* Lucene 10.5.0 on JDK 25 (`java -Xmx1g`, as Lucene's `gradle run`), measured
  once per algorithm as the reference (median of 3 runs, or the latest run,
  on a quiet host); Rucene
  built with the release profile and measured once per iteration, repeated
  only when the host was perturbed.
* Metric: R/L, the ratio of Rucene's elapsed time to Lucene's, per algorithm
  (total) and per operation. Below 1.0, Rucene is faster.
* Host: AMD Ryzen 9 5900HX (16 logical CPUs), 30 GiB RAM, Linux 7.0.0, x86-64.

**Result at `2c4f248c`:**

| Measure | R/L |
|---|---:|
| Algorithms faster in Rucene (total) | **17 of 20** |
| `standard` | 0.70 |
| `micro-standard` | 0.56 |
| `highlights` | 0.64 |
| `Warm` (operation) | 0.42 |
| `collector` | about 1.16 |
| `sort-standard` | about 1.11 |
| `sloppy-phrase` | about 1.07 (search on the same index: 1.36) |

The FINDING reports these values only; the other 14 faster algorithms are
not listed there individually. The operations still slower than Lucene are
listed under [Known limitations](#known-limitations).

**What changed:** 40 `perf` commits across `store`, `codecs`, `index`,
`search`, `analysis` and `util`, each faithful to Lucene's algorithms and file
formats; safe vectorisable kernels where Lucene vectorises (#685); and a
build target of `x86-64-v3` on x86-64 Linux (see
[Compatibility](#compatibility)).

## Compatibility

* **Lucene:** Apache Lucene Core 10.5.0 only, as in 0.1.0. The new modules
  follow Lucene 10.5.0's own; `rucene-analysis-icu` embeds ICU4J 77.1, the ICU
  version Lucene 10.5.0 uses.
* **Rust:** every crate declares `rust-version = "1.100"` and
  `edition = "2021"`. Built and tested with rustc 1.100.0 (2026-11-09).
* **CPU:** on x86-64 Linux, `.cargo/config.toml` builds this workspace for
  `target-cpu=x86-64-v3`, so binaries and tests built here require AVX2, FMA
  and BMI2. A crate that depends on `rucene` does not inherit the setting.
* **Features:** unchanged: `default = ["std", "mmap"]`; `zlib-c` makes
  `BEST_COMPRESSION` stored fields byte-identical to Lucene's.

## Build and test

```bash
cargo build --release              # the rucene crate
cargo test --workspace             # every workspace crate
cargo fmt --all -- --check
```

`lucene-highlighter`, `lucene-spatial3d`, `lucene-spatial-extras`,
`lucene-benchmark`, `lucene-analysis-icu`, `icu4j` 77.1, `spatial4j` 0.8,

and `commons-compress` (the list is in `tests/sprint17_oracle/mod.rs`).

## Known limitations

The complete, sourced list is in
[`CHANGELOG.md`, Known limitations](../../CHANGELOG.md#known-limitations).
In short:

* **Slower than Lucene on three algorithms**: `collector`, `sort-standard` and
  `sloppy-phrase`; and on some operations: `standard` `SearchSameRdr` about
  1.09–1.17, `sort-standard` `MAddDocs` 1.21 and `CloseIndex` 1.50,
  `collector` `ForceMerge` 1.27.
* **Open performance findings**: `collector` memory growth (about 280 MB per
  round, not traced), store-slice allocations per query, the UTF-16 term
  buffer (#686, in the backlog).
* **CPU requirement** for builds made in this workspace on x86-64 Linux:
  AVX2, FMA and BMI2.
* **20 Lucene modules are not ported**, among them `join`, `grouping`,
  `suggest`, `expressions` and `backward-codecs`.
* **Not on crates.io:** the crate name `rucene` is taken there by another
  project.
* The 0.1.0 limitations on older index formats, `BEST_COMPRESSION` and Thai
  segmentation still apply.
